# M0 threat model

Scope: proposed multi-tenant agreement/escrow platform and audited repository HEAD; no penetration test or security certification performed. Canonical invariants: [escrow security](../architecture/escrow-security.md), [identity](../architecture/identity-treasury.md), [billing](../architecture/fees-billing.md). Severity is prospective impact before mitigation, not a claim of an exploitable deployed vulnerability. Owners below are accountable roles to assign by name before implementation.

Assets: principal and client fee deposits, app billing credits, participant consent, treasury and arbiter commitments, keys/session secrets, private evidence, tenant data, ledger history and chain observations. Adversaries: malicious app/tenant, dishonest client or worker, compromised staff/arbiter, external API attacker, RPC/indexer/webhook provider, dependency attacker and privileged infrastructure operator. Trust boundaries: browser↔app↔API, app API key↔participant signature, console role↔on-chain authority, API/worker↔DB, evidence store↔viewer, signer↔broadcast, RPC↔canonical chain, billing↔escrow.

## Required adversarial suites and release evidence

M1: asset parsing/bounds and tenant constraints with populated migration fixtures. M2: Base Sepolia full transaction traces and fuzz/invariant tests for conserved balances, replay, reentrancy, invalid tokens, consent, immutable arbiters, deadlines and failed transfers. M3/M4: role unions, distinct-person approvals, invitations, wallet control and recovery. M5: ledger conservation/property tests and concurrent reserve/capture/reorg. M6/M7: two-sided evidence, access isolation, proposal races and threshold verdict execution. M8: full CKB VM transaction tests, supported wallet witnesses, malformed args, `since`, insufficient capacity, multi-lock-group output reuse, malicious authorizer locks and backward-compatible v1 spends. M9: SDK/webhook compatibility and duplicate/out-of-order delivery. M10: provider failures, process crash recovery, restore, key compromise drills, independent security review, alert ownership and regulatory review.

Host Rust unit tests and mocked RPC tests cannot establish transaction-level lock security. External review must cover each deployed contract/script and authorization integration. Track findings to closure or explicit risk acceptance by accountable owners; no mainnet movement until gates in [milestone contracts](../architecture/milestone-contracts.md) are satisfied. BTC requires independent Bitcoin-specific review; swap integrations need verified routes and provider failure contracts before implementation claims.
